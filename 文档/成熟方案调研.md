# 成熟方案调研：文本清洗 / 信息提取 / 检索

> 调研时间 2026-11-15。目标：把工作流里"自己写"的部分尽量换成有出处、有维护、有基准的上位方案。
> 每一条都查过 GitHub / PyPI / 官方文档的实时状态（star、最近提交、许可证、pip 名、wheel 是否含 cp312-win）。
> 判定三档：**采用**（能直接替换且收益明确）/ **参考**（算法值得抄或部分可用）/ **不用**（不适用，写明为什么）。

---

## 一、先给结论：按"能删掉多少自研代码"排序

| 优先 | 替换什么 | 换成什么 | 收益 | 风险 |
|---|---|---|---|---|
| 1 | 第 1 项：手写编码回退链 | `chardet 7` + `charset-normalizer` 双引擎投票 | 准确率 84% → 99%（作者自报），且不再用 `errors='replace'` 悄悄吞掉错字 | chardet 7 只有一个月历史，指标为作者自报，须自己 A/B |
| 2 | 第 2 项：70% 的手写清洗正则 | `ftfy.fix_text` + UTS #39 `confusables.txt` skeleton + `regex` 库 | 全角/实体/换行/控制符/mojibake 全部现成；同形字水印有了权威数据源 | ftfy 不删零宽字符；NFKC 会破坏中文排版，只能局部用 |
| 3 | 第 3 项：错别字词表 | `pycorrector 1.1.4` 的 `custom_confusion` + `proper_name` 两个外挂入口 | 词表从代码里搬进配置文件，专名保护用倒排索引（4 万词提速约 80 倍） | 模型在成人向文本上会过纠，必须只接受白名单内的高置信改动 |
| 4 | 第 5 项：分句 + 超长段 reflow | `wtpsplit`（SaT 模型，`lang_code='zh'`） | 一个 API 同时给句界与 60–170 字约束切分，且 `''.join(segments) == 原文` 可完美重建 | CPU 上跑全库是小时级，须预跑一次把 offset 落库 |
| 5 | 第 11 项：自研 bigram FTS5 | `tantivy`（`Tokenizer.ngram(2,3)`）或 `wangfenjin/simple` 的 FTS5 扩展 | 索引体积减半（6,276KB→3,068KB），中位延迟 0.38→0.28ms，自带 BM25 与 snippet | `simple` 的 .dll 需与 SQLite ABI 匹配，Windows 上要先实测 |
| 6 | 第 7 项：自研 containment | `datasketch.MinHashLSHEnsemble`（专为 containment 设计）+ `SetSimilaritySearch`（段级精确） | containment 不用手写；段级用精确 all-pairs，零漏检 | datasketch 2.0 换了置换方案，旧持久化索引必须重建 |
| 7 | 第 13 项：LLM 调用的 JSON 兜底 | `instructor` + `pydantic` | 字段类型与 `Literal` 枚举在 API 层被约束，标签只能从白名单选，重试退避内置 | 只是编排层，模型还得自己有 |
| 8 | 第 10 项：性别用字表 | `ngender`（朴素贝叶斯，2000 万条姓名统计） | 82% 准确率、零依赖、4µs/次 | 真人姓名口径，网文昵称/道号会掉点，只能当先验 |
| 9 | 第 8 项：手写人名规则 | `HanLP 2.1` NER（PER）+ 自定义词典 | Apache-2.0，2026-10 仍在发版，CPU 可跑 | 自造人名仍需词典兜；共指不在开源包里 |
| 10 | 第 8/9 项：别名聚类 | Stanford CoreNLP 中文 `deterministic-chinese.properties` | 中文共指 F1 47.5（neural 53.9），输出的是人物簇不是成对判断 | GPL-3.0、1.5GB 中文模型、要 JVM |

## 二、逐环节对照

### 2.1 编码检测与读文件（第 1 项）

**现在的做法**：`open(encoding='utf-8', errors='replace')`，失败回退 `gb18030` / `utf-16`，手写 BOM 判断。

**问题**：`errors='replace'` 会把误判静默变成 `U+FFFD`，永远不知道文件读错了。全库 464 部里必然有 gb18030 与前后拼接的混合稿。

| 方案 | 许可证 | 安装 | 判定 | 依据 |
|---|---|---|---|---|
| **chardet 7.7.0** | 0BSD（7.x 起，旧版是 LGPL） | `pip install chardet` | **采用** | 2026 年从零重写，13 阶段流水线（BOM→magic→结构探测→字节合法性→bigram）。自报 3,138 文件准确率 99.7%，同批 charset-normalizer 86.6%、旧 chardet 84.4%。UTF-8 判定校验全部字节而非采样 |
| **charset-normalizer 3.5.2** | MIT | `pip install charset-normalizer` | **采用**（第二意见） | 3.5.2 修了"合法 UTF-8 中文因生僻 CJK 噪声被误判 PTCP154"——这条只会咬我们这种语料。`from_path()` 直接给 `chaos/coherence/language/alphabets`，可对 464 个文件批量打质量分筛出读坏的 |
| cchardet 2.4.1 | MPL-1.1/GPL/LGPL 三选一 | `pip install cchardet` | 参考 | 中文编码表最全（含 HZ-GB-2312、EUC-TW），但准确率 94% 是三者最低，许可证是文件级 copyleft。只当第三裁判，不进主路径 |
| DuckDB 2.0 | MIT | `pip install duckdb` + `INSTALL encodings;` | **采用**（批处理壳） | `read_text(glob)` 一条 SQL 扫完 464 个文件；`encodings` 扩展支持 gb18030/big5/EUC_CN/EUC_TW |
| Polars 2.1 | MIT | — | 不用 | 55MB 文本用不上列式 SIMD；字符串正则会逐元素回调，实际慢于纯 Python；引入几十 MB 编译依赖换来 0 行自研代码被删 |
| textpipe 0.12.2 | MIT | — | 不用 | spaCy 2 时代产物，停更，且会把 spaCy 重依赖拖进来 |

**没有现成方案的（必须自己写，约 15 行）**：目录级/全书级投票调度——整本 detect 一次定基调，再按 4KB 切块各自 detect，只在块判决与基调冲突时逐块回退。所有检测器都只管单块字节。

**三段串联也是自研（约 10 行）**：`detect(raw)` → `raw.decode(enc, 'replace')` → `ftfy.fix_text()`。没有库把这条链做成一条命令，ftfy 明确不管检测。

### 2.2 文本规范化与清洗（第 2 项）

**现在的做法**：一堆手写正则——全角转半角、零宽、竖线方框、拼音打码、HTML 实体、域名水印变体、分隔线、省略号。

| 方案 | 许可证 | 安装 | 判定 | 依据 |
|---|---|---|---|---|
| **ftfy 6.3.1** | Apache-2.0（带附加条款） | `pip install ftfy` | **采用** | 唯一"成熟+纯 Python+单依赖"的清洗底座。`fix_character_width` 管全角→半角（含 U+3000）、`unescape_html` 只解明确实体（避免 `this&not that` 误转）、`fix_line_breaks` 管 `\r\n/U+2028/\x85`、`remove_control_chars`、`uncurl_quotes`、`fix_encoding` 修多层 mojibake（`â€œ`、`Ã©` 这类我们目前完全没做）。设计目标是"宁可不动也不误改"，对 1847 万字体量是生死线 |
| **UTS #39 confusables.txt** | Unicode License v3 | 直接下载 163KB 文本 | **采用** | 同形字水印（西里尔 `т`/全角 `Ｌ`/希腊 `ι`/数学字母）的唯一权威源，Unicode 18.0（2026-08-06）。格式 `源码位 ; 目标序列 ; MA # 注释`，加载成 dict 做 `skeleton()` 迭代到不动点。PyPI 上 `unicode_security`/`unicode-confusables` 全部 404；`confusable-homoglyphs` 数据停在 2024-01，不如官方 txt |
| **regex 2026.11.9** | Apache-2.0 AND CNRI | `pip install regex` | **采用** | 换 import 就变强：`\p{Script=Han}`、集合差集 `[[a-z]--[qw]]`、`\X` 字素簇、变长 lookbehind、**模糊匹配** `(?:肉棒){i<=1,s<=1:[\u4e00-\u9fff]}`（把打码还原从白名单升级成允许 2 字插入）、`timeout` 防灾难性回溯 |
| pycorrector 1.1.4 | Apache-2.0 | `pip install pycorrector==1.1.4` | **采用** | 见 2.3 |
| clean-text | Apache-2.0 | — | 不用 | 纯西文导向，`clean()` 会删数字与标点，直接毁掉「第12章」与对话引号 |
| text-unidecode | Artistic-1.0 / GPL-2.0 | — | 不用 | 中文会被音译成罗马字，灾难性破坏；且 GPL 传染 |

**必须知道的坑（调研明确指出的）**：
1. **ftfy 不删零宽字符**：它保留 `U+200C–200F`、`U+202A–202E`、`U+2028/2029`，`U+200B` 也不在删除清单里。必须自己补 `re.sub('[\u200b-\u200f\u2060\ufeff]', '', s)`。
2. **NFKC 不能当清洗主武器**：它会把全角括号 `（）`、全角引号、全角冒号一律压成半角，对中文排版是破坏。只能按字符类白名单做局部 NFKC——我们原来的手写做法在这点上是对的。
3. **ftfy 许可证有附加条款**：禁止把源码贴进 AI 训练集或喂给生成式 AI。当运行时依赖 import 是正常用法，但不要把源码贴进任何提示词，并在仓库保留 LICENSE 与署名。

### 2.3 错别字 / 形近字（第 3 项）

**现在的做法**：手写词表（`闻然→闻言` 19、`猛得→猛地` 34、`白勺→的` 1、`三干→三千` 1、`曰后→日后` 5）。

| 方案 | 判定 | 依据 |
|---|---|---|
| **pycorrector 1.1.4** | **采用** | 6543★，Apache-2.0。关键不是模型而是它把词表变成了配置：`custom_confusion_path_or_dict` 收「错词 正词」空格分隔（我们的词表可以整表搬成文件，代码零改动）；`proper_name_path` 收专名白名单，v1.1.4 换成倒排索引（4 万词提速约 80 倍）。`correct_batch()` 返回 `errors:[(wrong, right, pos)]` **带位置**，可只改白名单内的高置信项 |
| ReLM（AAAI 2024） | 参考 | 47★，无 LICENSE，无 pip 包。论文 arXiv:2308.08796 主张 CSC 应"整句重写+插槽填充"而非逐字标注，跨域可迁移性更好——对我们的"大量专名与性词"的语料，这个 formulation 天然少误改。抄思路不抄代码 |
| ReaLiSe（ACL 2021） | 不用 | 需 GPU、需 bert-base-chinese 分字输入、效果已被 ERNIE-CSC 超越、多年未维护 |

**性能账（之前实测过，此处复核）**：Kenlm-CSC 9 QPS（CPU）→ 全库 24.5 小时；MacBERT-CSC 224 QPS 需 V100，CPU 慢 10 倍以上。**结论不变：不要模型全量扫库，走「倒排专名 + 混淆集」拿 95% 收益，模型只对可疑段落抽样复核。**

**官方给出的句子级 F1（V100）**：Kenlm-CSC 0.3409 / MacBERT-CSC 0.3993（SIGHAN-2015 0.8314）/ ERNIE-CSC 0.4353（SIGHAN-2015 0.8383）/ Qwen3-4B-CTC 0.8521（5 QPS，需 GPU，不选）。

### 2.4 分句 / 段落 / 章节边界（第 5、6 项）

**现在的做法**：手写中文句末标点切分 + `reflow.py`（阈值 `MIN_SPLIT=220 / TARGET_MIN=60 / TARGET_MAX=170 / HARD_MAX=260`，`BAD_HEAD` 排除切点后的虚词）+ 手写章标题 regex。

| 方案 | 许可证 | 安装 | 判定 | 依据 |
|---|---|---|---|---|
| **wtpsplit（SaT）** | MIT | `pip install wtpsplit` | **采用** | EMNLP 2024 "Segment Any Text"，85 语言含 zh，multilingual macro-F1：sat-3l 89.2 / sat-3l-sm 93.5 / sat-6l-sm 95.1 / sat-12l-sm 96.0（同表 PySBD 英文仅 69.6）。中文内置先验 `lang_code='zh'` → `target_length=45 spread=15`，正好在我们要的 60–170 区间调。`sat.split(text, do_paragraph_segmentation=True)` 顺手给段落切分。`''.join(segments)==原文` 可完美重建 |
| HanLP EOS 断句模型 | Apache-2.0 | `pip install hanlp` | 参考 | `hanlp.pretrained.eos.UD_CTB_EOS_MUL`，UD2.3+CTB9 训练，中文在训练集内。但只给句界、没有 min/max length，60–170 约束仍要自己写，且拖 torch |
| zhon | MIT | `pip install zhon` | 参考 | 不给算法，只给权威字符类（CJK 标点、全半角、中文数字范围）。收益是"硬编码字符集换成有出处的常量" |
| chonkie | MIT | `pip install chonkie` | 参考 | RAG chunking 库，`RecursiveChunker` 的 delim 层级递归 + `chunk_size` 约束可当"按句切完再打包成 ≤N 字"的调度器。若已用 wtpsplit 则多余 |
| **pysbd** | MIT | — | **不用** | 读了 `pysbd/lang/chinese.py` 源码：中文实现只继承通用规则，`AbbreviationReplacer.SENTENCE_STARTERS = []`，`BetweenPunctuation` 只做三件事（保护《》、保护「」内标点、保护引号括号内标点）。**中文能力 = 「。！？」+ 引号保护，比我们手写 regex 更弱**，还多一层逐字符状态机开销。README 的 97.92% 出自英文 Golden Rule Set，与中文无关。2021 年后无新版 |
| novel-downloader / legado / koodo-reader | AGPL-3.0 / null / AGPL-3.0 | — | 不用 | 它们的"章节规则"是给 DOM/EPUB 用的 XPath/JSONPath/selector DSL，输入是已结构化章节，不是"一坨没有换行的 60 万字 txt"。legado 主仓源码已被删除（仓库 size 仅 52KB），拿不到那套正则 |
| so-novel（抄逻辑） | AGPL-3.0 | — | 参考 | 唯一把章标题识别写成独立可读单元的项目（`ChapterFilter.java`，9028★）。可抄两条：`TITLE_NUMBER_PATTERN = ^(\d+)\s*\.\s*(.+)$` 把「1.章名」归一化成「第1章 章名」；删重复标题时用 `Pattern.quote` 防章名里的正则元字符 |

**没有现成方案的**：
- **章标题双锚恢复**（第 6 项）：GitHub 上纯 txt 分章生态天花板是 `txt2epub` 58★、`novel-split` 10★ 这类千行个人脚本，零 pip 包零基准，且它们都假设"标题行还在"，而我们要处理的是"标题已被排版层剥掉、需回插"。**自研是对的**，只建议两处加固：`re.escape` 处理章名里的正则元字符；把「1. 章名 / 1、章名 / 第一章 章名 / Chapter 1」归一化成统一形式再入库。
- **TextTiling / C99 / BERT 篇章分割**：中文小说对话密集、词汇分布平坦，且真实段落边界在 txt 里往往已丢失，无监督信号无从锚定；C99 的 O(n²) 在 55 万字符上爆炸。SaT 的 `do_paragraph_segmentation=True` 是这条路唯一"有论文+85 语言基准+pip 一行"的可用物。

### 2.5 相似去重与近重复（第 7 项）

**现在的做法**：`datasketch` MinHash LSH（已用）+ 自研段级 24 字前缀去重 + 自研 8-gram containment 判同文/续篇。

| 方案 | 判定 | 依据 |
|---|---|---|
| **datasketch 2.0.0** | **采用**（升级用法） | 2980★，MIT。关键：**`MinHashLSHEnsemble` 专为 containment 阈值查询设计**（Zhu et al., VLDB 2016 LSH Ensemble），"短章 vs 全书""全书 vs 续篇"本质是 containment 不是 Jaccard，可以直接删掉手写 containment。另有 `MinHashLSHForest`（top-k）、`WeightedMinHash`。注意 2.0 默认置换方案改为 affine32，哈希值与旧版不兼容，持久化索引必须重建 |
| **SetSimilaritySearch** | **采用**（段级精确） | Apache-2.0，同作者。All-Pair-Binary + position filter 的**精确** all-pairs，支持 `similarity_func_name="containment"`，零漏检。README 实测比 `MinHashLSH(num_perm=32)` 更快，而后者 precision 0.73 / recall 0.67——判同文要"一个不漏"时精确法反而划算。边界：只在段级（200–2000 字）用，整部 46 万字的 8-gram 集合内存会爆 |
| text-dedup | 参考 | 765★，Apache-2.0，要 Py≥3.12。可抄的**硬数字**（CORE 2020-05-10）：MinHash macro-F1 0.9518 / acc 0.9277 / 11.09s；SimHash F1 0.8515 / 626.11s；NEWS-COPY ARI MinHash 0.7293 vs SimHash 0.6463——这是"用 MinHash 不要用 SimHash"的实证。可抄配置 `num_perm=240, threshold=0.7, ngram_size=5, hash_bits=64`。它是脚本仓库不是库（强绑 HF datasets+parquet），不采用 |
| copydetect | 参考 | 327★，MIT。MOSS 系 winnowing 指纹（k-gram 哈希 + 窗口取最小，保证任何 ≥k 的公共串必被选中），能给"这一章 1/3 处抄了那一章"的**带位置**局部匹配。只有约 200 行算法值得抄 |
| simhash | 参考 | 只适合"每段 8 字节定长指纹进 SQLite"的预筛；主判据不要用它（见上 F1 差 10 点、慢 50 倍） |
| semhash | 参考 | 978★，MIT，活跃。model2vec + vicinity ANN，纯 CPU，180 万条约 74 秒，`potion-multilingual-128M` 覆盖中文。但我们的语料高度同质（同样的身体词与场景模板），静态句向量会把"不同作品的同类场景"拉成大簇，只用于生成候选对/离群检测 |
| dedupe / dolma | 不用 | dedupe 是记录级实体消解+主动学习，需要字段式 blocker，连续散文没有字段；dolma 为万亿 token 设计，1847 万字连 Bloom 都嫌重，`dict[段落哈希]` 30 行就够 |

**没有现成方案的**：**同一作品不同版本/续篇识别**。必须复合信号自建，按信噪比排序：①章标题序列对齐（`rapidfuzz.process.cdist`，百级标题很快）②段级 containment 命中率 ③人名集合 Jaccard ④首章/末章双锚。**把它做成"结构化指纹"而不是纯文本相似度，这部分保留自研是对的。**

**另外**：464 部 all-pairs 只有 10.7 万对，全量精确计算秒级完成，**此处上 faiss/ANN 是纯过度设计**，不要引入 GPU 或 sentence-transformers 做全局近重复。

**没有中文近重复的权威榜单可引**：SIGHAN 是中文拼写纠错、CoNLL 是依存解析，都与此环节无关，别拿来背书。可引实测只有英文 CORE / NEWS-COPY，中文只能自建 200 对小验证集定阈值。

### 2.6 中文全文检索（第 11 项）

**现在的做法**：SQLite FTS5 + 自研 bigram 落库（因为 trigram 查不了 2 字词，unicode61 对中文等于不分词），查询侧也 bigram 化。

| 方案 | 许可证 | 判定 | 依据 |
|---|---|---|---|
| **tantivy-py 0.27.0** | MIT | **采用** | 有 cp312 win_amd64 wheel。`Tokenizer.ngram(min_gram=2, max_gram=3)` 原生 bigram；`add_pre_tokenized_text` 可喂 jieba 分词；`SnippetGenerator`/`phrase_query`/`doc_freq` 齐全。**实测同语料（620,899 字 / 8,883 段）：索引 6,276KB→3,068KB（减半），中位延迟 0.38→0.28ms，2 字查询 26/26 全中，建索引 18s（全量约 9 分钟）**。纯本地目录、零服务进程 |

### 2.8 角色共指与出场分析（第 8/9/10 项）

**现在的做法**：百家姓+称谓后缀+末字白名单+动作词打分（第 8）；coverage/spread/mentions/chap_ratio 四维加权（第 9）；人工 TSV + 名字用字（第 10）。

**三个必须直说的空白**：

1. **「主角判定」没有任何现成库**。核过 GitHub、HuggingFace、ACL Anthology：不存在 protagonist/character-importance 的可 pip 包。最强可抄基线是 BookNLP 的 `count + quotes + mentions`；学术侧只有 Labatut & Bost《Extraction and Analysis of Fictional Character Networks: A Survey》（ACM Computing Surveys 52(5):89, 2019, DOI 10.1145/3344548）提供"角色网络 → 用中心性衡量角色重要性"的方法论，但不出代码。**所以第 9 项不是"找个库替换"，而是"换输入源"**：把 coverage+次数+跨度+节数四维，改成 CoreNLP 人物簇 + 台词归属 + 按章计数 + 图中心性（networkx 三行）四个更硬的信号。

2. **⚠️ 我之前引用 Mendenhall 特征曲线是错的，必须纠正**：Mendenhall（1887）的 composition characteristic curve 是**词长频次分布曲线**，用于作者归属/作品分期（stylometry），**跟角色出场无关**。我上次把它当成"出场范围"的经典依据，属误用。真正要的"出场曲线"标准操作就是按章聚合 mention/quote 计数画折线，pandas 十行，不存在库。Moretti 的 distant reading 是方法论框架不是软件。

3. **中文共指的离线路线只剩两条**：CoreNLP（GPL-3.0 + 1.5GB jar + JVM）或 LLM 逐章聚类。没有第三条捷径。Stanza 有 zh-hans 的 NER/POS/依存（Apache-2.0，可作第 8 项备选），但 coref 明确无中文模型。

**建议落地顺序**：先上 CoreNLP 中文 deterministic（F1 47.5，快且不吃显存），把人物簇接到第 8/9 项；同时用 ngender 替掉名字用字表，代词占比从 CoreNLP 的 mention 结果反推；HanLP 只兜 NER 与句法，不管共指。BookNLP 不进生产，只当 schema 规格书。

## 三、诚实清单：这些环节确实没有比自己写更好的现成方案

| 环节 | 为什么没有 |
|---|---|
| 章标题双锚恢复 | 纯 txt 分章生态天花板是 10–58★ 个人脚本，且都假设标题行还在 |
| 防和谐断词还原（`肉，棒`→`肉棒`） | PyPI 上不存在中文断词还原包。最多改用 `pyahocorasick` 提速 |
| 拼音打码还原（`Rou棒`→`肉棒`） | 没有库。最接近的上位是 `regex` 模糊匹配 `(?:肉棒){i<=1,s<=1:[\u4e00-\u9fff]}` + 骨架化，阈值仍要自己调 |
| 竖线/方框装饰符与分隔线 | 无库，属排版私货 |
| 目录级编码投票调度 | 检测器都只管单块字节，整书基调 + 4KB 分块投票要自己写（约 15 行） |
| 同作异名/续篇识别 | 没有库，必须复合信号（章标题序列 + containment + 人名 Jaccard + 首末章双锚） |
| 主角判定 | 没有库，只能换输入源（见 2.8） |
| 中文题材分类 | 没有可用模型（THUCNews 系都是新闻栏目，个人上传无维护无 license） |
| 零宽字符清理 | ftfy 明确保留 `U+200C–200F`、`U+202A–202E`，不含 `U+200B`，必须自己补一条 |

## 四、落地顺序（按"改动小 + 收益大"排）

1. **编码层**（只改读文件那 30 行）：`chardet 7` + `charset-normalizer` 双引擎投票 → `decode` → `ftfy.fix_text`。先用 464 部跑 A/B，看两引擎一致率与人工抽 20 部。
2. **清洗层**：手写正则保留（装饰符/分隔线/断词这些确实无库），但全角/实体/换行/控制符/mojibake 交给 ftfy；零宽自己补一条；同形字水印换 UTS #39 skeleton（**仅对含非 Han 混排的行启用**，避免误伤日文假名正文）。
3. **错别字层**：`词库\typos.txt` 转成 pycorrector 的 `custom_confusion` 格式（错词 正词 空格分隔），`guard.txt` 转成 `proper_name` 一行一词。只接受 `errors` 里 position 落在白名单命中项的改动。
4. **分句/分段层**：wtpsplit 预跑一次，把句界 offset 落库，生产不跑模型；比对它与我现有 reflow 的输出，抽 50 段看切点差异。
5. **检索层**：tantivy 建并行索引，与我现有 bigram FTS5 做同查询集对比（延迟、召回、体积），确认后再切。
6. **去重层**：`MinHashLSHEnsemble` 替掉手写 containment；段级用 `SetSimilaritySearch` 精确法。
7. **角色层**：ngender 先替代用字表；HanLP NER 与现有规则做召回/准确率对比；CoreNLP 共指单独试一章。
